# 两容器一键部署候选方案（待确认，未实现）

用户提出将项目从单纯前端升级为上游 OpenList 后端 + 二改前端 + 独立图标服务，一条安装命令启动两个 Docker 容器。此文件是方案，不是可执行部署承诺；不修改现有实例。

## 上游基线

已通过 GitHub API 查验，OpenList 最新稳定 release 当前为 v4.2.6。应锁定验证过的 tag/镜像 digest，不能把未经验证的浮动 latest 称为兼容版本。上游后端许可证为 AGPL-3.0，分发修改后端须保留许可、来源、修改说明及提供对应源码；第三方素材授权另审。

## 容器划分

- openlist：上游 OpenList 后端 + 编译后的二改前端，版本化镜像；默认 dist_dir 指向镜像内完整前端，不要求初装用户手工复制。
- icons：独立 PNG 素材服务，私有 catalog/原图/预览/trash 数据卷，真实 OpenList 管理员验证与在用删除保护。
- Compose 统一网络、数据路径、重启策略、健康检查与版本；安装脚本下载发行配置、检查 Docker/端口/已有目录并启动，不覆盖原数据或占用现有容器名称。
- 图标服务只在内部网络公开给 openlist，用户只访问一个站点端口；无需独立图标域名/证书/CORS或向任意第三方发送凭据。

## 必须明确选择的同源入口实现

仅把服务放进同一 Compose 网络并不会自动让浏览器访问 /icon/。要满足两个容器 + 单一入口：

A. 对 OpenList 后端做最小路由扩展（推荐，但须明确授权修改后端）：在 SPA fallback 之前增加 /icon/ 反向代理到固定内网 icons 上游，Authorization/Origin 原样传递；不开放任意目标 URL，不改存储/账号/文件API业务。则 openlist 容器仅原后端进程，icons 容器仅图标进程。

B. 保持官方后端二进制完全不变：需要在现有两容器之一增加网关进程，或增加第三个网关容器；前者引入多进程镜像，后者不再是两个容器。该取舍不能隐瞒或声称未经修改后端天然能转发 /icon/。

先让用户选择 A 或 B，禁止提前实施对上游源码的改动。

## 发行与用户体验

- Releases 同时提供版本化安装配置、前端独立包和源码；保留旧用户只换 dist/ 的入口。
- 新用户一条命令启动配套两个容器，图标管理自动使用同源 /icon/，显示健康状态/测试连接，无需填接口地址。
- HTTPS 站点上线仍需用户提供网站域名/证书，除非以后另行明确开发证书自动化；不能宣称仅 Docker 命令已完成 DNS/SSL。
- 根目录下统一 data/ 与 icon-data/；备份需保证数据库一致性，镜像归档不含绑定挂载数据。
- 首次安装与已有 OpenList 迁移分开；已有站点必须备份、确认兼容、保留回滚，不自动将生产 openlist 替换。

## 实施前验收条件

确定后端修改许可；审查公开仓库历史/敏感数据/素材授权；完成版本固定、Compose和安装脚本幂等/冲突/失败回滚测试；验证实际两个容器、内网鉴权、HTTPS同源访问、图标上传删除/读回、OpenList文件业务与前端回归。仅源码写出不算部署完成。
